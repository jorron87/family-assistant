# Oppsett for din familie

1. Installer Node.js 24+ og Chrome på Windows. Klon repoet til en egen mappe. Kjør `npm ci`, `npm run setup`, `npm run doctor`.
2. Rediger `config/profile.json`. Velg stabile, unike medlems-ID-er, navn, `role:parent|child` og eventuelle aliaser som matcher portalens fornavn. Ikke bruk «jeg» som et globalt person-alias; mobilinnboksen kjenner avsenderen. Sett `vigilo:false` på barn som ikke skal dekkes i Vigilo. Profilfilen er startprofil for **nye** arkiver; eksisterende profiler redigeres via GUI/CLI og overskrives ikke ved oppstart.
3. Sett `backfillFrom`, kalender-ID og privat Drive-mappe i `config/sources.json`. Velg en passende historisk start; importer ikke et annet prosjekts historie. Legg bare til Facebook-grupper husholdningen allerede har tilgang til. Alle profiler/ID-er i eksemplene er oppdiktet.
4. Start `npm start`. Lokal agentport4318, kiosk4319 og mobil4320 bruker loopback. Bruk en separat `FAMILIEN_DATA_DIR` ved utvikling. Ikke pek en testinstallasjon på produksjonsarkivet.
5. Åpne `chrome://extensions` i den Chrome-profilen familien skal bruke, aktiver utviklermodus, velg «Last inn upakket» og mappen `config/vigilo-keepalive`. Les manifestets tillatelser. Logg inn i Vigilo/Spond på vanlig måte. Behold én kildefane per tjeneste; ikke kopier cookies eller tokens. Sett `config/collector.json.enabled:true` når innhentingen er ønsket. Vent på ferske faktiske samlerkvitteringer per barn/flate. Facebook kan kreve besøk/scrolling for at innholdet lastes.
6. Koble til Google på `/google-setup` med egen OAuth-klient og de nødvendige tillatelsene, eller bruk agentens egne autoriserte Drive-/Calendar-verktøy. Følg `google-status`/`publish` i runbook. Opprett gjerne en separat testkalender først. Drive og kalender må være tilgjengelige for de valgte familiemedlemmene på telefon.
7. Konfigurer `config/agent.json`: full sti til egen agent-CLI, en modell kontoen faktisk støtter, reasoningEffort og eksplisitte valg av sandbox/approvalPolicy. Standardmodellen er tom og automatikk avslått. Start med én manuell gjennomgang og kontroller kilder, kalender, oppgaver og deling. Ved unattended drift kan en interaktiv approval-policy stoppe på verktøykall; velg dette bevisst sammen med systemeieren, og gi bare den tilgangen oppgaven trenger.
8. Etter bestått manuell test: aktiver agenten og ønsket `collector.dispatch`. Mobilbehandling starter når egen global lease er ledig. `dailyFullFallback:true` kan starte daglig reservekontroll etter07:15 norsk tid. Avtal eventuell planlagt fullkontroll og daglig drift i agent-appen. Repoet oppretter ingen abonnementer eller app-automasjoner automatisk.

## Handel (valgfritt)

Hjemmeskjermen og den tilknyttede mobilvisningen har «Avklaringer» med korte svaralternativer. Agenten samler nødvendige familievalg der; samme spørsmål deles på tvers av varer. Velg avsender når du svarer. Svarene lagres også når agenten er pauset, og behandles med den allerede godkjente agentkonfigurasjonen når den kan kjøre. Ubesvarte spørsmål starter ingen agentkjøring. Se runbookens avklaringskontrakt; ingen ny modell- eller verktøytilgang er nødvendig.

Egne eller ennå uavklarte familiebeslutninger går til vanlig familiegjennomgang. De parallelle varearbeiderne kan utvide en allerede valgt bred familie innen gjeldende krav, men kan ikke erstatte et slikt familievalg. Arbeidet beholdes i kø og fullføring; denne rutingen krever ingen ny innstilling.

Når handel, Oda-tilkobling og `collector.dispatch` er aktivert, oppfrisker tjenesten kjente gjennomgåtte Oda-priser med kode uten agentstart. Se runbookens «Varejobber og automatisk rutinearbeid» for avgrensning, pauser og status. Automatisk prislesing gir ingen kurv- eller variantgodkjenning.

Sesum kan supplere kjedeprisene gjennom den eksisterende Chrome-utvidelsen. `config/shopping-sesum.example.json` er avslått som standard; opprett en privat `config/shopping-sesum.json`, velg kjeder som faktisk brukes, og prøv innhentingen med syntetiske familier i separat datamappe før aktivering. Last inn den oppdaterte utvidelsen og bruk én ledig Sesum-fane. Samleren leser bare offentlige søke- og varesider på `https://www.sesum.no`; den kopierer ingen cookies og oppretter ingen Sesum-konto. Tilgangsfeil og rategrenser gir pause, ikke omgåelse.

Innhentingen dekker alle aktiverte varefamilier, alle resultatsider som kilden faktisk lenker videre til og alle oppdagede varer. `shopping-sesum` viser fremdrift per familie og kjede; innhenting er forskjellig fra godkjente produkter og ferske priser. Gjennomgå nye kildebroer med `shopping-sesum-candidates` og `shopping-sesum-review` før prisene brukes. Nye varianter uten eksisterende gjennomgått donor behandles som `shopping-sesum-discovery`: undersøk faktisk innhold og pakning, og registrer dem med `shopping-sesum-register`. Manglende EAN er ikke et automatisk avslag, og en ny gruppe blir aldri automatisk et familievalg. En priskvittering uten faktisk prisdato blir aldri fersk av hentingen. API-et og de krypterte innhentingskvitteringene er bare tilgjengelige på agentporten. Se Sesum-kontrakten i runbooken.

Kampanjer på godkjente Sesum-varer gir egen `shopping-sesum-offer-review` til den vanlige handelsagenten. Agenten leser `shopping-sesum-offers`, kontrollerer faktisk annonsepris og vilkår hos primærkilden og registrerer et ordinært tilbud med varig kampanjekvittering. Produktidentitet frigir aldri ukjente medlems-/mengde-/periodevilkår. Endrede vilkår holder tidligere tilknyttede tilbud tilbake på alle prisflater; uendrede faktiske primærlesinger kan fornyes uten ny produktgodkjenning. Mobil og kiosk kan ikke godkjenne kampanjer.

Godkjent Sesum-identitet er også adskilt fra husholdningens familievalg. Kontroller `shopping-sesum-family-review` etter både priskobling og ny registrering: en vare i en ny bibliotekgruppe krever fortsatt eksplisitt `shopping-family-set`, et konkret scoped avslag eller blokkert restanse. Kildeinnsamling, produktgodkjenning og familiedekning er ulike fullføringskrav.

Ved familieendringer gjenbruker koden bare dokumentert uendrede vurderinger. Eldre hel-sett-kvitteringer kan få kriteriegrunnlaget tilbake gjennom en eksakt kontrollert historisk hash; ukjent grunnlag gjennomgås fortsatt. Enhetsavslag krever en gjeldende godkjent kildepakning og vises som kodebevis i `reviewDelta`, aldri som en produktgodkjenning. Konkrete kildeblokkeringer beholder sine frister og forblir synlige som ufullført arbeid. Se runbookens inkrementelle plasseringskontrakt.

En ustabil MCP-forbindelse gir avgrenset nytt leseforsøk og tydelig transportdiagnostikk. Skriving med mistet svar gjentas aldri automatisk. Bevar proposalId og kontroller domenets faktiske kvitteringer; faktiske sikkerhetsstopp krever fortsatt gjennomgang før gjenopptakelse.

En stopp forblir låst over omstart og vanlig retry. Etter konkret eier-/autorisert operatørgjennomgang kan agentportens `shopping/review-stop` registrere en fingerprintbundet kvittering og be om ny kjøring gjennom ordinære gater. Dette er ingen automatisk godkjenning av en verktøypolicy eller ukjent skriveresultat. Se runbooken før operasjonen brukes.

Før et «ingen relevant familie»-avslag får arbeideren spørsmål også fra discovery-familier og gjennomgåtte gruppekandidater, ikke bare ordrett familienavn. Inkrementelle spørsmål gjelder bare endrede/uavklarte familier. Kode normaliserer en manglende tom målliste bare når den uttrykkelige negative vurderingen eller blokkeringen allerede er tilstrekkelig dokumentert; positive mål og ukjente produktfakta utledes aldri.

En kildepakning oppgitt som antall kan sammenlignes i kg/l først etter et særskilt `countedPack`-bevis for hele pakkens faktiske nettoinnhold. Det krever samme antall som native metadata og faktisk primærlesing av samme pakke. Koden endrer ikke rå pakningsdata eller prisdato og bruker aldri varenavn som vektbevis. Se runbooken før denne kontrakten benyttes; ukjent mengde og reelle motstridende opplysninger forblir blokkert.

`shopping-sesum-placement-review` lar agenten undersøke hver aktuell kildevare mot alle aktive familiekrav, også uten treff i familiens kildesøk. `shopping-sesum-placement` viser hele det gjeldende settet. En eksplisitt researchkvittering ruter arbeidet videre og endrer ingen familiegodkjenning, pris, råhint eller handlekurv. Ukjent plassering forblir en varig blokkert restanse.

Prisfrie egne observasjoner får kjedenøytral `sesum-product:ID` og samme hele-familiesett-research. Et relevant produkt uten faktisk konfigurert kjedepris forblir en konkret blokkert katalogoppgave, uten oppdiktet butikk, pris eller familiegodkjenning. Tidligere lagrede observasjoner importeres lokalt med opprinnelige tider, uten ny kildehenting. Ukjent prisalder blir aldri fersk, og kjent gamle faktiske kvitteringer parkerer uendret metadata også når en ny prisfri observasjon kommer. Les katalogkontrakten i runbooken.

Løsvekt kan først brukes som aktuell kg-/literpris etter eksplisitt direct-unit-review av faktisk salgsform, produkt, grupper og brutto/MVA-grunnlag. Hver pris må ha en validert egen synlig kjederad-label; varen beholder null pakkemengde og pakkepris. Installer og test den faktisk valgte utvidelsesbuilden før katalogens snevre `missing-direct-unit-basis-v1`-reparasjon brukes på utvalgte eldre fullførte jobber. Bruk bare serverens eksakte jobb-ID/fingerprint/build-beskrivelse, aldri en ny full innhenting eller gjettet én-kilos pakke. Les løsvektkontrakten i runbooken.

Et privat gjennomgått produktbibliotek kan kobles til med `config/shopping-library.json` etter eksempelfilen. Aktiver først etter kontroll av egen fil og egne watch-godkjenninger. Fellesprismodellen bruker da nyere kvitteringer fra identiske godkjente native produkter i alle handlevisninger. Biblioteket godkjenner ingen familievalg, oppretter ingen overvåkninger og endrer ingen kurv; se runbookens avsnitt om felles aktuell pris.

Bibliotekleserens `compare` kan også vise versjonert råvarescore fra dokumentert ingrediensinnhold, uten ekstra oppsett eller nettinnhenting. Den gjelder bare støttede kategorier med gyldig produktreview. Manglende mengde eller ulikt målegrunnlag forblir synlig; score er ingen samlet helsevurdering og aktiverer ingen kjøpshandling. Se runbookens avsnitt om dokumentert råvarekvalitet.

Varegrupper kan sammenligne gjennomgåtte varianter fra forskjellige merker. Den løpende agentkontrollen må både oppdage nye produkter og kontrollere endringer i innhold/pakninger. Katalogen legger slike endringer i egen gjennomgangskø, mens uendret metadata beholder vurderingen. Bruk `shopping-catalog-observe` og `shopping-catalog-review` etter runbooken før nye varianter tas med i prisguiden.

Prisguiden kan lagre `targetPrice`, `excellentPrice` og et datert `priceGuide`-grunnlag per overvåkning. Kjøpsgrenser er husholdningens justerbare planleggingsvalg. `shopping-market FIL` lar serveren opprette `marketCalibration` fra gjennomgått Kassal-historikk, med normalmedian av daglige sammenlignbare lavpriser, en bra-grense begrenset av aktuell markedspris og eventuell lavere fersk alternativreferanse, og en særskilt svært-bra-grense bare ved dokumentert vedvarende eller gjentatt lavpris. Den avledede prishistorikken følger det gjennomgåtte varegrunnlaget; endret grunnlag arkiverer den tidligere serien og bygger en ny fra validerte observasjoner. Et utilstrekkelig nytt grunnlag kan ikke videreføre gammel automatisk markedsguide, mens manuelle grenser bevares. Det er et selvstendig markedsgrunnlag, ikke en fast rabatt på tidligere Oda-pris. Kronebesparelsen bruker likevel alltid den laveste tilgjengelige referansen: markedsmedian, dokumentert betalt produktpris og ferske sammenlignbare alternativer. En høyere markedsmedian skal ikke blåse opp gevinsten mot en billigere pris familien har betalt.

Hver produkt/kjede-kobling må ha `reviewed:true`, konkret `equivalenceEvidence`, riktig total pakningsmengde i kg/l/stk og pakkepriser inkludert dokumentert moms. Faktisk aktuell priskvittering må være høyst 48 timer gammel; hentetid fornyer ikke prisens alder. Et 90 dagers historikkall kan gi langt færre observerte dager. Kontroller faktisk dato-, kjede-, produkt- og hulldekning etter runbookens kontrakt før grensene brukes. `insufficient` viser at ny markedskalibrering mangler; tidligere planleggingsgrenser kan beholdes med unntak av automatisk markedsguide fra endret eller udokumentert varegrunnlag. En flat eller sparsom serie skal ikke få et oppdiktet svært-bra-nivå. Kalibrering oppretter verken tilbud, forbruksanslag eller kurvendringer.

Kassal-integrasjonen er valgfri: konfigurer familiens egen API-nøkkel med `kassal-configure` som beskrevet i runbooken. Nøkkelen lagres kryptert på agenten og skal aldri legges i offentlig config, logger eller klientkode. Kjedepriser supplerer kildekontrollen; de bekrefter ikke lokale kampanjer eller lagerstatus. Hobbytilgang og tilgjengelige kjeder må kontrolleres mot Kassals gjeldende dokumentasjon.

Handel kan bruke `purchaseAmount` for planlagte storinnkjøp av lagringsvarer. Dette er et alternativ til `monthlyUsage`, ikke målt forbruk. Se handelskontraktene i `runbook.md`; velg mengder og varselgrenser etter husholdningens preferanser og varenes faktiske holdbarhet.

Handel-fanen viser kjøpsanalyse, en overvåkningsliste og kildebelagte tilbud. Overvåkning er avslått ved opprettelse. Åpne `/shopping-setup` på agentporten for å koble til familiens egen Oda-konto via OAuth og `https://oda.com/mcp`. Familien godkjenner tilgangen hos Oda; registrering og tokens lagres kryptert i eget dataområde og vises aldri i dashboard-API-et. Ikke kopier nettlesercookies eller en annen installasjons tokens. Oppsettet er sperret på kiosk- og mobilporten. Hent historikk og prøv én uttrykkelig valgt kurvendring manuelt før tilkoblingen regnes som testet. Familien betaler på Odas nettside.

Når Oda er tilkoblet, prøv `oda-refresh-plan` og én målrettet `oda-refresh FIL` for en allerede gjennomgått varefamilie. Dette leser bare aktuelle priser og tilgjengelighet via MCP; det godkjenner ingen ny variant og endrer ingen kurv. Agentkøen oppfrisker kjente produkter før prisene utløper. Ukjent/utgått priskilde skal behandles som en prisrestanse fremfor et nytt manuelt familievalg.

Bruk `shopping-settings` til historisk startdato, lagringsnotat og eksplisitt valgte butikker med stabile ID-er, offisielle kundeavislenker og minste besparelse per handletur. Valgfri `chainCode` identifiserer butikkens Kassal-kjede ved markedssammenligning, slik at et tilbud sammenlignes med ferske alternativer hos andre kjeder framfor sin egen kampanjepris. Uten kjent kjedekode brukes alle aktuelle kjedepriser som en forsiktig begrensning. Tersklene er familiens praktiske prioritering, ikke en måling av kjørekostnad. `monitoringEnabled:true` legger forfalte butikkontroller i den eksisterende agentens `next`-kø; det oppretter ingen ny automatisering, runtime eller modell. Kilder må kontrolleres manuelt før aktivering. Bruk runbookens shoppingkontrakter og test med syntetiske ordre i separat datamappe først.

Handelsagenten får høyst 20 frosne varejobber og leser paginert kontekst med `shopping-agent-context`/`shopping-agent-page`. `shopping-agent-decide` binder plasseringsbeslutninger til gjeldende fingerprints i kode. Prøv den isolerte `scripts/benchmark-shopping-agent.mjs --execute` før større kjøringer; den bruker syntetiske data og endrer ingen dispatchinnstillinger. Valgfri `dispatch.shoppingProgressGapSeconds` i collector-konfigurasjonen gir raskere fortsettelse bare etter en faktisk lagret gyldig vurderingskvittering. Den aktiverer ikke en pauset agent, og vanlig kilde-/familieprioritet og feilpauser består. Se runbook for kommando- og kvitteringskontraktene.

Valgfri `dispatch.shoppingWorkers` er 1 som standard, og kan settes til 2 eller 3 etter isolert test med `node scripts/benchmark-shopping-coordinator.mjs --execute --cases=140`. Koordinatoren beholder én kjørelås og tildeler høyst 20 hele varejobber til hver arbeider. Arbeiderne bruker den allerede valgte modellen/nivået, en read-only sandbox og fire eksplisitt tillatte, oppgaveavgrensede shopping-MCP-verktøy. Shell, apper, plugins, nettleser og underagenter er deaktivert for disse prosessene. Bare koordinatoren utfører validerte domeneskrivinger; dette endrer ingen global Codex-konfigurasjon. Et nytt oppsett krever fortsatt eierens uttrykkelige valg av modell, verktøy og ubetjente tillatelser. Innstillingen aktiverer ingen pauset agent eller samler. Se runbook for restanser, nettleserarbeid og avbrudd.

Før full researchkjøring må også offentlig etikettlesing, checkpoint, produktregistrering og eksplisitt familietilknytning verifiseres i et isolert arkiv. En plasseringstest med ferdige etiketter beviser ikke dette løpet. Kontroller komplette agentdossierer, faktisk slutt på biblioteksøk og sikker tilbakekalling ved korte/ugyldige stoppbegrunnelser. Ingen slik test skal bruke produksjonsarkivet eller aktivere produksjonsinnstillinger.

Dispatch forbereder den avgrensede kontekstfilen i kode og leverer hele produktbolken direkte ved oppstart når datadelen er innenfor 400000 tegn; store pakker bruker paginering. Komplette familiekriterier leveres først som et stabilt oppstartsgrunnlag når de passer; kontekstleseren gjenbruker dette bare ved identisk fingerprint. Nye indekser bevarer også full produkttekst for agentarbeid, mens vanlige visninger fortsatt bruker korte utdrag. Eldre indeksformat bygges på nytt automatisk. Arbeidspakken tilbyr kun fortsatt gyldige, gjennomgåtte donoropplysninger; familiebruk og prisbelegg har egne kontroller. `--mode=packet --inline-context` måler denne oppstartsflyten i den isolerte benchmarken.

Før større kjøringer kan `--dataset=expanded --mode=packet --inline-context --compact-bindings --repetitions=1 --effort=high` brukes til 140 unike produkter mot 91 konkrete familier. `--chains=3` tester separate kjeder innen samme produktjobb. Bekreft både kvalitet og tid; null feilaktige familietreff eller utrygge avklaringer er et eget krav. Benchmarken endrer ingen modell-, tillatelses- eller dispatchvalg i produksjon. Rene plasseringsbolker lar kode binde tekniske fingerprints fra den komplette kontekstfilen, og CLI gjenbruker bare faktisk levert input med identisk kontekst- og familiefingerprint.

Valgfri `--parallel=2 --batches=0,1` sammenligner samtidige, isolerte testarbeidere. Hver arbeider har eget syntetisk arkiv; dette aktiverer ingen parallell produksjonskjøring. Der eier fortsatt én koordinator kjørelåsen og må fordele identiteter og validere domeneskrivinger.

Oda dekker ikke nødvendigvis hele matbudsjettet eller forbruket. Kostholdsanalyse trenger næringsdeklarasjoner og målbar mengde; den gjetter ikke næringsinnhold eller barnas energibehov fra handlekurven.

Før daglig bruk av Lager: test en fritekstmengde og to overlappende bilder i separat testdataområde. Kontroller at den valgte agenten starter, faktisk leser begge bilder, teller én fysisk samling én gang og frigjør egen lease. Prøv også uklare etiketter, nyere manuell beholdning, avbrutt opplasting og Angre. Lager støtter JPG/PNG/WebP; eksporter HEIC som JPG. Bilder og tellingshistorikk lagres privat kryptert, uten automatisk Drive-/kalenderpublisering. Lagerinnsendinger bruker den eksisterende familiehandlingsdispatcheren også når prisovervåkning er av. ## Mobil utenfor hjemmenettet

Sett en HTTPS-tunnel/reverse proxy til **bare port4320** og `/send/`; bruk egen adresse i `config/phone-access.json`. En tunnel på samme PC kan nå loopback direkte. Ved LAN-bruk må `FAMILIEN_PHONE_HOST` settes uttrykkelig og brannmur begrenses passende. Åpne `/phone-setup` lokalt på4318 for å lage en tidsbegrenset invitasjon/QR. Velg riktig avsender per telefon og legg siden på hjemskjermen. Invitasjoner og enhetstilgang er hemmeligheter. Test utlogging/tilbakekalling og ekte bilde/tekstinnsending før familiens daglige bruk. Bare den valgte agenten behandler data; ingen eksterne AI-kall gjøres av prosjektet uten agentoppsettet.

## Windows og Raspberry Pi

Familievisningen er laget for en permanent **24-tommers touchskjerm i 16:9, 1920 × 1080**, sentralt i huset: et vakkert og nyttig møbel familien bruker sammen. Monter i en høyde barna kan nå. Store trykkflater, touchrulling og tilbakeføring til oversikten etter inaktivitet er tilpasset denne bruken. En separat laptop/mini-PC driver løsningen; skjermen eller Pi-en viser den. Mobilvisningen fungerer i tillegg.

`scripts/install-web.ps1` installerer en lokal Windows-oppgave under den nåværende brukeren. Kjør bare fra den nye installasjonen. Oppgavene må ha tilgang til samme DPAPI-bruker. Pi-en kan kjøre `scripts/dashboard-kiosk.sh` som bruker-tjeneste fra `scripts/dashboard-kiosk.service`. Kopier skriptet til `~/.local/bin/familien-kiosk` og gjør det kjørbart. Tilpass display/Wayland/X11 til Pi-OS. Installer et SSH-alias `dashboard` med verifisert vertsnøkkel; `install-dashboard-tunnel.ps1` videresender kiosk/gateway til loopback på Pi. Ikke eksponer agentporten som kiosk. Oppsettet er et utgangspunkt; display- og tunneloppsett må testes på den faktiske maskinen.

## Akseptanse før automatikk

Tunnelens gjenstartsforsøk kjører uten konsollvindu, også når Pi-en ikke svarer. `scripts/enable-dashboard-recovery.ps1` oppgraderer en eksisterende direkte SSH-oppgave til skjult oppstart uten å avbryte en aktiv tunnel. Den lille Windows Script Host-starteren genereres lokalt i `.local/runtime`; aktiver ikke deaktivert Windows Script Host for å omgå en maskinpolicy. Ringeklokkens arbeider gjenbruker en allerede kjørende gateway og skriver standardfeil separat i `gateway-error.log`.

- En ny ukeplan er fullstendig lest, gir riktig dato og pakkeliste, og originalen kan åpnes fra telefon.
- Ny gjennomgang av uendret plan lager ingen nye nedlastinger eller kalenderdubletter.
- Søsken har individuelle avkryssinger. Skjul/gjenåpne synkroniserer med testkalenderen.
- En utløpt økt gir synlig dekningshull og et forståelig varsel.
- Mobil tekst/bilde behandles straks lease er ledig; lokal visning og kalender samsvarer.
- Gjenstart av web/PC bevarer data, låseregler og familiens valg.

## Optional whole-assortment library

Copy shopping-assortment.example.json to the ignored config/shopping-assortment.json. Keep enabled and collectionEnabled false until the source contracts, actual price dates and scoped workers have been tested. Whole-assortment mode uses the existing encrypted Kassal API configuration and the installed Chrome extension (1.9.0 or newer). With familySource:"sesum", Sesum is the category/product master and Oda is imported separately through the read-only MCP product search. Kassal enumeration is disabled in this mode. The independent reviewed-library compatibility mode can enumerate Kassal products with no search filter, unique=0 and size=100. Both modes use Sesum's public category index/pages with no household chain/promotion filters. Public catalogue requests omit session cookies so household site preferences cannot narrow the sweep; authenticated/private endpoints are not used. Ordinary search/product collection remains available when the mode is disabled.

The optional priceHorizonDays defaults to 14. This selects recently priced library products; it is not proof of local stock. The original household/history horizon and stricter 48-hour actionable-price checks remain separate. Products, reviews and native chain identities are preserved when parked. Actual receipt dates are required; fetchedAt and product updated_at do not refresh a price.

Large catalogue observations and semantic reviews are stored in a separate encrypted transaction repository under the instance data directory, not inside the household archive. Include the assortment directory and assortment-collection transaction files in private backups together with the existing encryption key. Do not copy another household's data or key. A partial/invalid encrypted transaction fails closed and requires recovery from the actual preserved journal/backup; never delete it to claim completion.

Start the bounded household category plan with shopping-taxonomy and shopping-taxonomy-bootstrap; the durable source whitelist automatically pauses after its selected receipts. This never resumes unrelated source jobs or starts an agent. Native IDs/names/hierarchy are preserved; household stock, need and exact variant records remain intact.

Starting full collection is explicit. shopping-assortment-start accepts a UTF-8 JSON file with validationReads:1 through 8 for a bounded live validation; its durable budget cannot turn into a full sweep on restart. Pause collection with shopping-assortment-pause. Resume an existing sweep only when the owner has authorized it. Enabling this config never enables an agent runtime, changes models/permissions or bypasses the dispatch pause.
